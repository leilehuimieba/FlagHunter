## 0. 一句话定位

北极星 V3 把项目按**零件柜**（tools / strategies / knowledge 各一格、分层不变量守边界）建模得很好。
但用户的设想是另一条正交的轴——**装配线（kill-chain 工序流水线）**。当前代码只显式建模了零件柜，
**没有把"工序流水线"和"黑板协同"做成一等公民**。本文的全部问题都围绕"把零件柜升级成一条会学习的
装配线"展开。

## 1. 愿景（用户拍板，作为设计约束）

### 1.1 一套通用骨架，项目类型 = profile 覆盖层（不分三条线）

CTF / 授权代码审计 / 攻防演练**本质同一条装配线**，不做三套代码。差别只是**进场信息**与**取舍**不同，
表达为"项目档案 / profile"的覆盖配置：

| 项目类型 | 进场信息 | 取舍重点 |
|----------|----------|----------|
| CTF 靶场 | 给 URL（有时给源码），知道大致走向 | 激进、走最短链、按已知信息直奔 flag |
| 代码审计 | 给源码 | 怎么审、怎么查漏洞、有没有 0day（白盒优先，回灌可疑点到线上验证）|
| 攻防演练 | 黑盒目标 + 规则 | 准备什么、保守先确认、留痕可复盘 |

> 现状：已有 `exploitation_mode`（CTF 激进 / 渗透保守）是这条 profile 轴的**雏形**，但还不是一个完整的
> "项目档案"抽象（进场信息形态 + 工序取舍 + 终止准则一起切换）。**这是 P12。**

### 1.2 运行方式 = 黑板架构 + 多智能体外放探索（不追求单 agent 包打）

- **黑板意识**：多个智能体围绕一块共享黑板工作，各自张贴发现 / 读取他人发现。
- **外放探索**：派不同智能体去探不同攻击面。
- **每个 agent 的协议**：先试"**一步到位**"（能直接出 flag/拿权就出）；**不行就退而求其次**，
  采集对下一轮进攻有用的信息张贴到黑板，**让下一次进攻更好**。
- **核心难点 = 多智能体编排**（派谁、采什么、够了没、何时停、怎么把分散发现汇成下一步）。

### 1.3 模块化铁律（贯穿全部问题）

> "我希望项目模块化程度高，未来有更好的优化可以直接替换或者更新。"

每一块能力 / 编排器 / 记忆后端都必须是**可替换单元**：边界清晰、有接口契约、有测试守、
被 import-linter / reachability / taxonomy 三道治理钉住，不允许某次"更优方案"要推倒一片才能换。
**用户当下给的方案不一定最优，所以接口要稳、实现要可换。**

## 2. 运行方式目标形态（装配线 + 黑板）

```
进场(profile: URL / 源码 / 黑盒目标)
   │
   ▼
[轻侦察] 先看站点/指纹/版本/加载了什么 ── 不上来全端口全目录扫(笨)
   │  └─ 已知漏洞? → 查知识库(RAG) / 联网搜索(可投入做更强搜索)
   ▼
[攻击面登记] 潜在攻击点真假判定 → 找入手点  ← 统一登记+可达性评分(现缺)
   │
   ▼
[假设生成] 复用历史链(高匹配→按实况改) │ 无历史→从漏洞原理/可疑点推
   │                                   └─ 复用必配负反馈(不出活就降权)
   ▼
[攻击执行] 回显? → 直检测 ；黑盒/无回显? → 盲测/带外(现弱)
   │  多智能体: 先试一步到位 ; 不行→退而求其次采信息 张贴黑板, 下轮更好
   ▼
[取 flag / 拿访问] ──► [经验回灌] 调用链留痕 → 涌现序列挖成可复用链 → 更新记忆
                                        ▲
                    黑板: 各 agent 张贴/读取, orchestrator 据黑板决定下一步派发与停止
```

**判断：器官（侦察、RAG、策略、记忆、crew）大半已有；缺的是工序之间的"传送带 + 反馈线 + 黑板"，
以及编排的停止准则。真正的杠杆不在"再加能力"，在编排策略 + 记忆/溯源闭环。**

## 3. 上线问题清单（"距离完善还差几个问题"）

按"地基 → 编排 → 学习闭环 → 能力 → 纪律 → 既存债"分层。每条标注：现状 / 为什么重要 / 模块化落点。
**优先级：地基层先行（没有调用流水，编排与回灌都是无源之水）。**

### 地基层（先做）

**P1 — 工序流水线没做成一等公民**
现状：代码按零件柜组织，kill-chain 工序散落在各 mixin / 链里，没有显式"阶段"对象。
为什么重要：profile 取舍、停止准则、留痕都需要挂在"阶段"上才有落点。
模块化落点：定义可插拔的 Phase 抽象（侦察/攻击面/假设/执行/回灌），各 profile 只覆盖阶段策略。

**P2 — 黑板还不是一等公民的协同面**
现状：notes（loot/notes.json）+ ShadowGraph + crew 有"共享状态"雏形，但不是干净的黑板：
没有统一的"张贴 / 订阅 / 据黑板决策"协议；Cairn 黑板研究文档已有蓝图但未完全落地。
为什么重要：多智能体外放探索 + "退而求其次张贴信息供下轮"全靠它。
模块化落点：黑板接口（post/read/subscribe）+ 可替换后端；orchestrator 只依赖接口。

**P3 — 工具调用溯源 / 遥测层（provenance）几乎为空**【用户最看重、最缺】
现状：能看到某工具"被用过几次、单用还是和谁组成链、结果如何"的调用流水——**基本没有**。
ShadowGraph 消费的是 notes 不是工具调用流。
为什么重要：这是 P5（涌现链挖掘）、经验回灌、编排决策、"调用链可见"UI 的共同地基。
模块化落点：executor 旁路一个 provenance 记录器（不侵入工具实现）→ 可查询/可视化层。

### 编排层

**P4 — 多智能体编排 + 停止准则（"够了没"）**
现状：crew（orchestrator + worker pool + ShadowGraph）有骨架；spawn_mcp_agent 可层级派生。
缺"够了没"的终止策略 → 有无界扇出风险。
为什么重要：用户核心难点就是这个；"不够就继续派 agent"必须有刹车。
设计主张：**"信息够了" = 已产出一个可测试假设，且其对应策略可达**——把"派不派下一个 agent"
绑到"有没有新的可测假设"，**不绑"还能不能再扫出点啥"**（避免覆盖数字当目标）。
模块化落点：派发策略 / 终止策略做成可替换 policy 对象，profile 可覆盖。

**P5 — 项目类型 profile 抽象（统一骨架 + 取舍覆盖）**
现状：`exploitation_mode`（CTF/渗透）是雏形，但不是完整"项目档案"。
为什么重要：用户明确"不分三条线，用 profile 覆盖"。
模块化落点：Profile = {进场信息形态, 各阶段策略, 派发/停止策略, 激进度}；CTF / 代码审计 / 攻防演练
各一份配置，骨架不变。

### 学习闭环

**P6 — 涌现工具序列 → 可复用链挖掘**
现状：strategy_memory 按"策略种类"存，不按"涌现出来的工具序列"存——中间有真实空白。
为什么重要：用户的"复用历史攻击链"要靠这个把成功的调用序列沉淀成有名字的链。
依赖：P3（没有调用流水就挖不出序列）。

**P7 — 复用匹配质量 + 负反馈配对**
现状：负反馈回路 D1 已闭合；但"高匹配就照搬"仍是 force-fit 风险家族。
设计主张：复用机制**必须**和负反馈成对（链不出活就降权/丢弃），否则记忆库越长越脏。

**P8 — 经验回灌闭环半残**
现状：strategy_memory + learned_rules（N1 已复活）+ 负反馈 D1 已做；蚁群 M5 悬空（D3 暂缓）；
skills 体系缺失。
为什么重要：用户要"持续更新记忆库"。
模块化落点：回灌写侧 3 链统一走门面（N3c-2 待迁）；记忆后端可替换。

**P9 — skills 体系 + 治理（如采纳）**
现状：无 runtime skills 概念。
设计主张/反驳：先问"是否真需要 skills 这个新原语"——也许所谓 skills = 已有的 tools + strategies +
playbooks 的组合/模板，缺的是**编排/模板**不是新原语。**若**真要引入 skills，必须配
registry + 防 rot 治理（对标 tools/strategies 的 taxonomy 标注 + reachability），否则重造 god-module 债。

### 能力补全

**P10 — 黑盒 / 盲测 / 带外（OOB/OAST）**
现状：检测器强依赖回显（canary、反射 marker）；唯一带外种子是 open_redirect 的 `.invalid` canary。
为什么重要：用户要"黑盒自己分情况"，真盲（时间盲注、带外）现在几乎没有。
模块化落点：盲测/带外作为独立检测后端，与回显检测并列可插拔。

**P11 — 更强的搜索 / 知识检索模块**
现状：RAG（dense+BM25+RRF）+ web_search（Tavily）已有。
用户意愿：愿意花时间研究"更好的搜索"。
模块化落点：检索器接口稳定，dense/BM25/web/未来更强后端可整块替换。

**P12 — 攻击面统一登记 + 可达性评分面板**
现状：每条链各自鸭子 probe 判真假，没有统一"攻击面登记 + 真假/可达性评分"面板。
为什么重要：用户要"判断潜在攻击点真假、找入手点"，且要可见。
依赖：与 P3 provenance、P2 黑板天然耦合。

### 纪律 / 边界（贯穿，写成守则不是一次性任务）

**P13 — LLM 编排 vs 承重的硬界限**
守则：LLM 决定"调哪个、怎么编排、参数填什么"；**真正承重、要可复现、可测试的那一步必须落在工具里**。
不让 LLM 亲自当 exploit。守 O1=C 控制面哲学（代码守底线、模型只重排）。

**P14 — 工具自建 vs 下载的边界**
守则：(a) 常备工具箱（Kali 镜像 + 注册工具）优先；(b) LLM 可写**一次性 payload**（不落注册表）；
(c) 把一次性脚本提拔为正式工具必须是**人审过的显式动作**，禁止运行时自动固化（防垃圾债砸模块化）。

### 既存结构债（与本愿景强相关的）

**P16 — 入口渠道注册表 + 热插拔（入口轴 / 模块化）**
现状：入口分发是 ``interface/main.py`` 里一条**写死的 if/elif 链**（按 argparse 动词跳）。
真正的"输入渠道"（监听/服务面）有 4~5 个：TUI、Web 控制台（127.0.0.1:8080）、MCP-SSE
（**0.0.0.0:8080** ⚠️ 默认全网卡）、MCP-stdio、MCP 控制 socket（~/.flaghunter/mcp.sock）。
**渠道层没有注册表、没有配置驱动的 enable/disable、没有运行时开关**——唯一的 enable/disable 是
``mcp enable/disable``（开关**上游外部** MCP server，非自己的渠道）和工具的 ``enabled`` 标志。
为什么重要：用户要"方便关闭某个输入渠道 / 开启新渠道"；且默认 0.0.0.0 是真实暴露面（红队工具
不该默认把控制面绑全网卡）。
模块化落点：**把工具层范式搬到渠道层**——定义 ``Channel`` 抽象（name/serve/enabled）+ 自注册 +
loader 发现；``main()`` 的 if/elif 换成"查注册表→起启用渠道"；配置门控（关一个=改一行配置，
加新渠道=新增自注册模块不碰分发）；顺手把监听类默认收回 127.0.0.1，要 0.0.0.0 显式开。
两条边界：①只纳入"监听/服务类渠道"，CLI 工具动词（coverage/workspace…）不动；②先做"配置门控
（重启生效）"=90% 价值，运行时真·热切换（agent 跑着起/停监听器）留后续，别一上来追。
**自包含、不依赖黑板地基，可独立于地基波随时插入。**

**P15 — 策略逻辑本体（run-fn）god-module**
现状：策略的"逻辑本体"塞在大 mixin 文件里（earlier ③）。L4b 已证：链执行体未完全对象化，
`_execute_chain` 有 ctx-blind seam；**并行收益 = "无并行单元可开"（已被 L4b 证伪，别拿提速当目标）**。
为什么重要：直接关系用户的"模块化、可替换、可维护"。
落地取舍：目标是 A 可测试/隔离 + B 可换/可删 + C 降 god-module 债，**不是 D 提速**。

## 4. 距离"上线"的路线（地基 → 编排 → 闭环 → 能力 → 打磨）

每一步遵循用户节奏：**做 → 测试 → 优化 → 再下一步**；每步另起实施计划入记忆，按计划推进。

1. **地基波**：P3 provenance（最先，地基的地基）→ P2 黑板一等公民 → P1 Phase 抽象。
2. **编排波**：P4 多智能体编排 + 停止准则 → P5 profile 抽象。
3. **闭环波**：P6 涌现链挖掘 → P7 复用+负反馈 → P8 回灌门面收尾。
4. **能力波**：P10 盲测/带外 → P11 搜索增强 → P12 攻击面面板。
5. **打磨波**：P15 run-fn 对象化（模块化收尾）；P13/P14 守则固化为治理测试。
6. **上线**：端到端跑通三类 profile（CTF / 代码审计 / 攻防演练）各一个真实样例，回归全绿 +
   import-linter / reachability / taxonomy 三道治理全 KEPT。

> 注：P9 skills 故意不进主线——先判断是否真需要该原语（见 P9 反驳），需要才插入闭环波。

---

## 5. 模块化验收基线（每一步都要满足）

- 新增/替换的单元只 import 它该 import 的层（守 I1，import-linter KEPT）。
- 有接口契约 + 测试守；替换实现不需要改调用方。
- 若是策略/工具，必带 taxonomy 标注或显式豁免（防 rot）。
- 编排策略 / 记忆后端 / 检索器 / 检测后端均为**可替换 policy/后端对象**，profile 只覆盖配置。
- 任何"更优方案"都应能**整块替换**对应单元，而非推倒一片。
