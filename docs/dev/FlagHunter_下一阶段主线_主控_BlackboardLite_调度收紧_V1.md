# FlagHunter 下一阶段主线：主控 / Blackboard-lite / 调度收紧 V1

> 适用仓库：`D:\webstudy\FlagHunter`
>
> 适用阶段：在 Web Console 真值化收口之后，项目进入“主控判断能力收紧 + Blackboard-lite 落地 + 调度收紧”的下一阶段。
>
> 核心判断：**先会判断，再会跑。**

---

## 1. 下一阶段的唯一主线

当前阶段不要再把主线分散成很多平行目标。下一阶段只保留一条主线：

> **主控 / Blackboard-lite / 调度收紧**

这条主线的含义不是“再做一个大而全的 agent 系统”，而是：

1. 让系统先学会判断
2. 再让系统学会按判断去跑
3. 最后才考虑继续扩展能力面

---

## 2. 核心原则

### 2.1 判断先于执行

工具调用不是第一目标，工具调用只是判断之后的执行动作。

如果系统连下面这些问题都还没判断清楚，就不应该急着跑：

- 当前目标是什么
- 当前入口是什么
- 当前边界是什么
- 哪些事实已经确认
- 哪些结论还只是猜测
- 哪些东西值得优先验证

### 2.2 会跑依赖会判断

“会跑”不是指能调用更多工具，而是指：

- 能在正确的时机调用正确的工具
- 能解释为什么这一步要跑
- 能在跑完之后把结果重新写回事实层

### 2.3 TUI 不再是重点投入方向

后续不再把 TUI 作为主要建设对象。

当前更合理的人工/自动化组合是：

- **CLI**：执行面
- **Web Console**：观察面
- **本地脚本 / Python / PowerShell / Kali**：工具面

---

## 3. Blackboard-lite 要解决什么

Blackboard-lite 不是重型图数据库，也不是全量记忆中枢。
它只需要把最关键的项目认知层收出来：

1. **事实**
   - 已确认、可复用、可定位的信息

2. **猜测**
   - 还没验证，但值得推进的方向

3. **待验证结论**
   - 比猜测更强，但还不能当最终答案

4. **决策记录**
   - 为什么走这条路线
   - 为什么切换
   - 为什么停止

5. **执行产物**
   - 附件、脚本输出、日志、checkpoint、artifact

Blackboard-lite 的目标不是“看起来像智能板”，而是让主控和 worker 都能基于同一套事实做判断。

---

## 4. 调度收紧要做什么

调度收紧的核心不是“多派几个人”，而是“少猜、少乱跑、少上下文污染”。

### 4.1 先选最值钱的路径

优先级按下面顺序：

1. 离目标最近
2. 验证成本最低
3. 已有事实支持最多
4. 最容易回收成可复用链路

### 4.2 只在必要时扩散

允许“蚁群式向外扩张”，但不是平均扩张。

扩张必须满足至少一条：

- 能显著增加事实密度
- 能快速排除一个大方向
- 能把一次性操作变成可复跑链路

### 4.3 先收口，不先扩面

在样本和事实还不稳的时候，不要优先做这些事：

- 新的 UI 大功能
- 更多入口
- 更多 agent 角色
- 更复杂的 MCP 接入

---

## 5. 下一阶段优先级

### 优先级 1：主控判断

主控必须先能回答：

- 现在该不该跑
- 跑什么
- 为什么跑这个
- 跑完之后怎么判断结果

### 优先级 2：Blackboard-lite

把事实 / 猜测 / 待验证结论 / 决策记录分开。

### 优先级 3：调度收紧

把任务路由、工具选择、上下文装配和恢复策略收敛到更短的链路。

### 优先级 4：样本驱动验证

继续用本地 challenge / artifact / runtime 样本验证判断质量，而不是只看页面能不能点。

---

## 6. 明确不做什么

下一阶段先不做：

- TUI 继续投入
- 没有样本牵引的重构
- 先扩功能再补判断
- 继续把重点放在更多页面动作上
- 复杂 MCP 生态扩张

---

## 7. 文档与执行的最小同步规则

后续所有改动都要按这个顺序同步：

1. 先确认当前代码事实
2. 再更新对应文档
3. 再做最小任务
4. 再做验证
5. 再把结果回写到状态文档

## 8. 成功标准

这一阶段什么时候算“方向对了”，看下面几个信号：

1. 主控能明确说出下一步为什么做、为什么不做
2. 工具调用不再是盲跑，而是由判断驱动
3. Blackboard-lite 里能区分事实、猜测、待验证结论
4. 本地样本能持续逼出真实缺口
5. 文档不再跟实现脱节，且维护成本可控
