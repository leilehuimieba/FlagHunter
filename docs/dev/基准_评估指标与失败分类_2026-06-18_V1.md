## 0. 这条基准钉什么

要「优化」就得先有**可对比的尺子**。本项目自评「agent 真正会判断仅 50–60%」却长期说不清**卡在哪一步、是哪类失败**。本基准：

1. 冻结现有**失败分类**（recovery 已有 10 类动作，但散在字符串里、未成 enum）。
2. 定义**评估指标口径**（链成功率 vs 节点均值；最坏值）。
3. 钉死指标读数所依赖的**证据基底**（harness 三件套已落地）。

---

## 1. 失败分类基线（recovery 的 10 类动作）

`recovery.py:RecoveryController` 返回 `RecoveryDecision.action`（`:10`）。现以**字符串**区分、**无正式 enum**——这是首要待固化点。

| # | action | 含义 | 触发锚点 |
|---|---|---|---|
| 1 | `wait_for_provider_recovery` | 所有 LLM provider 不可用，等待 | `:25` |
| 2 | `switch_chain` | 当前链缺工具/假设耗尽 → 切下一 ranked 链 | `:73,146,161,187,254` |
| 3 | `stop_missing_tools` | 无可用工具且无备选链 | `:88` |
| 4 | `wait_for_verification` | runtime flag 已得但未验证（阻塞） | `:115,277` |
| 5 | `stop_candidate_only` | 仅 source-only 候选、无 runtime 证据、无备选 | `:128,290` |
| 6 | `stop_blocked_surface` | 均匀失败面（WAF/封锁） | `:200,308` |
| 7 | `explore_agenda` | 有优先探索项待办，先探再切 | `:214,238` |
| 8 | `stop_exhausted` | 活跃假设耗尽、无备选 | `:172` |
| 9 | `stop_no_progress` | 连续 N 轮零新信号 | `:261,321` |
| 10 | `stop_generic` | 兜底停 | `:330` |

> **目标态（C5/E5）**：① 把这 10 类提升为 `FailureCategory` enum（schema 变更记 [[CHANGELOG_schema.md]]）；② 区分**可重试 transient**（1）与**终止类**（3/5/6/8/9/10），只对前者抖动重试，**绝不重试** ValueError/TypeError；③ 每类映射一条 `failure→hint` 喂下一轮（`recovery.py` 现仅处理 provider 不可用，缺真熔断 + 映射表）。

## 2. 评估指标口径

### 2.1 链感知 / 最坏值（替代节点均值）—— E4

攻击是乘法链：节点各 90% × 4 步 ≈ 66% 端到端。只看「找到几个凭据」（节点均值）会掩盖「几条端到端链真的解了」。**承诺口径**：

- **分阶段成功率**：`recon → foothold/auth → exploit → flag` 各阶段独立成功率。
- **端到端链成功率**：整链贯通率（首要北极星指标）。
- **最坏值 p0**：报最脆弱单步，而非均值——优化**对下游影响最大的那一步**。
- **成功判定来自外部状态**：flag 真被平台接受（见 [[基准_验证与解题判定_2026-06-18_V1]] S3），非 agent 自称。

### 2.2 预算分层（取代散落的 `max_steps=8`）—— C1

| 区 | 余量 | 策略 |
|---|---|---|
| 绿 | >50% | 正常 |
| 黄 | 20–50% | 压上下文、去 CoT、辅助调用切 mini 模型 |
| 红 | 5–20% | 仅核心调用，余皆降级 |
| 熔断 | <5% | 强制 finish，输出部分结果 |

落点：`BudgetGovernor`（待建）在 dispatcher 循环顶 + `CrewOrchestrator.run` 咨询。

### 2.3 失败归因占比（驱动优化排序）

按 §1 分类统计占比：`token`/熔断类高 → 上 HTTP 压缩与分层记忆（M2/M7）；`stop_no_progress`/`stop_exhausted` 高 → 假设多样性不足（C2 假设搜索树）；`stop_blocked_surface` 高 → 需绕过面策略。

## 3. 证据基底（指标从哪读，已落地）

`flaghunter/harness/` 三件套（JSONL、run_id 键）—— 指标与回归的真相源，**勿绕过直接信 agent 自述**：

| 模块 | 记录什么 | 关键方法 |
|---|---|---|
| `session_ledger.py` | 每 thought/tool-call/observation 的 append-only 事件流 | `append_event` / `read_events` / `tail_events` |
| `checkpoint_store.py` | 按 run 的状态快照（可恢复） | `save_checkpoint` / `latest_checkpoint` / `get_checkpoint` |
| `audit_events.py` | 标准事件 payload 工厂（dispatcher/tool/verification/recovery/checkpoint/artifact/task…） | `build_*_event` |
| `artifact_registry.py` | 按 run 的产物清单 | `register_artifact` / `list_artifacts` / `get_artifact` |

`retrospective.py`：`load/save_retrospective`、`get_unresolved_entries`；`_export_to_markdown` 现为 **stub（未完整导出）** → 待补，作为复盘出口。

> 目标态（E10）：`observability.py:MetricsCollector` 现扁平 → 分层 span（round-scoped Entry/Step + chain/skill span），键到 ledger 轮次，归因「哪条 chain 烧预算 / 出假 flag」。
