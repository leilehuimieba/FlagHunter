# FlagHunter 下一阶段路线（目标驱动 / Blackboard-lite / 本地工具优先）V1

> 形成时间：2026-05-31  
> 适用范围：`D:\webstudy\FlagHunter` 当前主线  
> 目的：把最近围绕 Cairn、Harness、Dispatcher、artifact 真值化的讨论，收敛成一份可执行的方向文档

---

## 1. 结论先行

当前阶段，FlagHunter 不应该优先演进成“依赖大量 MCP / 外部应用接入 / 复杂多进程编排”的系统。  
更合理的方向是：

> **把 FlagHunter 收敛成一个以目标为中心、以事实为真相、以调度为大脑、以本地 CLI / 脚本 / Kali 为主执行面、以 Blackboard-lite 为记忆层的智能执行系统。**

这个方向包含 4 个核心判断：

1. **目标优先于流程**  
   用户首先告诉 agent：目标是什么、当前入口是什么、边界是什么。  
   系统随后自己判断：能否一步到位、是否需要探索、先探哪条最值钱。

2. **事实优先于 prompt 幻觉**  
   上下文不能继续主要依赖长对话堆叠。  
   需要把事实、猜测、待验证结论、运行产物、决策记录分层保存。

3. **本地能力优先于重接入成本能力**  
   能用 CLI / Python / PowerShell / Kali 工具实现的能力，默认不优先走 MCP 或只能通过 GUI / 外部应用接入的能力。

4. **一边实战，一边优化**  
   不先追求“大重构完成再上题”，而是持续用本地样本题、压缩包题、源码泄露题、附件题去暴露真实缺口，再做最小修复。

---

## 2. 我们真正想要的 agent 形态

理想状态下，FlagHunter 的运行方式应当更接近下面这条链：

1. 输入：
   - 最终目标
   - 已知入口
   - 当前边界 / 限制

2. 系统判断：
   - 是否能直接攻击 / 验证
   - 是否需要先探索
   - 哪条探索路径最接近最终目标

3. 执行策略：
   - 优先低成本、高反馈、可验证、离目标近的路径
   - 探索可以扩散，但不是平均扩散，而是“高价值优先扩散”

4. 写回真相：
   - 新事实
   - 新猜测
   - 新待验证结论
   - 新产物
   - 新决策记录

5. 重新判断：
   - 是否值得继续同一路径
   - 是否触发新一轮 reason
   - 是否可以直接结束

---

## 3. 接下来采用的总体形态

我建议 FlagHunter 逐步形成下面 5 层，而不是一步到位做大重构。

### 3.1 目标层

这一层只保存最关键的输入：

- 最终要拿到什么
- 当前已知入口是什么
- 当前限制是什么

它的目的不是存很多字段，而是保证后续所有动作都围绕“任务卡”推进。

---

### 3.2 Blackboard-lite

先不做重型图系统，先做一个轻量黑板，保存 5 类信息：

1. **事实**
   - 已确认、可回放、可定位的信息

2. **猜测**
   - 还没证实，但值得继续推进的方向

3. **待验证结论**
   - 比猜测更强，但还不能当最终结果

4. **运行产物**
   - 下载物、脚本输出、分析结果、临时文件、日志

5. **决策记录**
   - 为什么当前走这条路线
   - 为什么停止或切换

Blackboard-lite 的目标，不是“看起来像图数据库”，而是给调度器和后续 agent 提供一个统一的真相层。

---

### 3.3 调度层

调度层负责判断：

- 现在是直接打，还是先探
- 先探哪条
- 哪些事情可以并行
- 哪些事情必须停掉
- 哪些状态变化值得重新推理

它的基本原则只有一句话：

> **优先走离目标最近、验证成本最低、已有事实支持最多的路径。**

---

### 3.4 执行层

执行层的优先级顺序必须收紧：

1. 本地 CLI
2. 本地 Python / PowerShell / shell 小脚本
3. HTTP / 浏览器自动化
4. Kali / 沙箱中的现成工具
5. 最后才是 MCP

原因：

- 更可控
- 更容易复现
- 更适合积累自己的工具包
- 更不依赖昂贵、脆弱、接入成本高的外部能力

---

### 3.5 知识层

建议保留本地知识层，但要轻量、分层、按需读取。

知识分 3 类：

1. **稳定知识**
   - 题型套路
   - 工具使用模式
   - 常见验证逻辑

2. **项目记忆**
   - 本项目里的真实运行经验、失败表面、约定

3. **样本复盘**
   - 具体题目成功/失败链路
   - 哪些事实最值钱
   - 哪些动作浪费时间

---

## 4. 上下文策略

不再依赖“把所有历史都塞进上下文”。

建议拆成 3 层：

### 4.1 当前短上下文

只保留：

- 当前目标
- 当前入口
- 最近确认的事实
- 当前正在推进的 1~3 条路径
- 最近关键失败点
- 下一步验证目标

### 4.2 冷记忆

需要时再拿：

- 历史 notes
- artifacts
- checkpoints
- 样本复盘
- 本地知识库命中

### 4.3 结构化状态摘要

由系统生成一份统一摘要，供主控和子 agent 使用：

- 已确认事实
- 当前候选路径
- 待验证结论
- 已知失败表面
- 当前推荐动作

---

## 5. 事实与猜测必须分开

接下来要把重要信息明确落到 4 类中：

1. **事实**
2. **猜测**
3. **待验证结论**
4. **最终结论**

规则：

- 事实必须有证据来源
- 猜测必须说明为什么怀疑
- 待验证结论必须说明怎么验证
- 最终结论必须有 stop / success 原因

这不只是记录习惯，而会直接影响调度与是否触发 reason。

---

## 6. 多 agent 协作方式

不是让很多 agent 同时乱跑，而是控制为 3 类角色：

### 6.1 主控 agent

负责：

- 看目标
- 看黑板
- 选路径
- 分派任务
- 合并结果
- 决定继续 / 停止 / 切换

### 6.2 执行 agent

负责：

- 针对单一路径做探索或验证
- 返回结构化结果

### 6.3 验证 agent

负责：

- 独立检查关键结论是否成立
- 尤其用于 flag、credential、利用成功判断

协作规则：

- 不共享整段对话历史
- 只共享黑板摘要、任务卡、必要证据
- worker 不直接写最终全局结论

---

## 7. Kali / 沙箱 / 本地工具包的定位

Kali 和沙箱不应只是“有，但没真正用起来”的能力。

建议明确定位：

1. **重工具执行器**
   - nmap / sqlmap / ffuf / nuclei / binwalk / sqlite / wal / pwntools 等

2. **脏活隔离区**
   - 下载、解压、批量分析、临时依赖

3. **标准工具包宿主**
   - 承载我们自己的可复用脚本与工具集合

主机侧偏向：

- 编排
- 调度
- 状态管理
- 轻量脚本

Kali 侧偏向：

- 安全工具
- 重分析
- 环境隔离

---

## 8. 下一阶段执行顺序

我建议按下面顺序推进，而不是大重构。

### 第一段：继续 artifact 生产侧真值化

重点收口：

- local challenge / artifactPaths
- recovery 产物
- retrospective / missing_tools / task 控制记录 与真正 artifact 的边界

### 第二段：做 Blackboard-lite 最小合同

先定义：

- run facts
- run action decisions
- reason trigger

不先上大图，不先做复杂 UI。

### 第三段：实战样本矩阵持续驱动

建议至少持续维护 4 条样本 lane：

1. runtime verified web
2. source-only candidate / false-positive guard
3. artifact-heavy / attachment-heavy
4. local challenge / packaged challenge

每次都按：

- 最小提示运行
- 找卡点
- 修最小一刀
- 重跑验证

## 9. 当前阶段的明确选择

基于现在的项目状态，我建议：

> **不优先做大 UI，不优先做独立 Blackboard Server，不优先做更重的 MCP 接入。**

而是优先做：

1. local challenge / artifactPaths 真值化
2. Dispatcher-only write path 继续收口
3. Blackboard-lite 最小合同
4. 持续样本驱动优化

---

## 10. 最终一句话

接下来 FlagHunter 的主线，不是“再堆更多能力”，而是：

> **让系统更像一个目标驱动、事实驱动、调度驱动、以本地工具/Kali 为主执行面的智能执行体。**

这比继续扩散能力边界，更接近我们真正要打造的东西。
