# CTF web 链可达性静态审计 V1（2026-06-17）

> 起因：[强网杯 2019]随便注 live 实测发现"SQLi 解题能力已写好但通用 web 分类够不着"（commit `dd58a1c`）。本审计把该单点发现**系统化**：枚举 `分类器可判类型 × 各 dedicated chain × web 链实际探测的策略`，一次性找出所有同构的"可达性缺口"。不烧靶机，纯静态。

## 关键机制

1. **分类器** `detect_type(page_source, url)`（`ctf_planner.py:320`）：**只看页面正文 + URL**，不看 cookie/header。输出 ∈ {misc, upload, lfi, ssrf, xss, sqli, jwt, web(兜底)}。
2. **链路由** `choose_chain_order(state)`（`hypothesis_engine.py:113`）：`detected_type`（非 web/auto）前插 chain_order，再按 hypothesis 追加，末尾永远兜 `web`。
3. **专链分发** `_execute_chain`（`ctf_dispatcher.py:2300+`）：按 `chain_name` 分发到 xss/web/misc/sqli/jwt/lfi/cmdi/ssrf/upload。
4. **web 链** `_execute_web_chain` 的 `_WEB_STRATEGY_ORDER`：hint_chain_followup / file_read_endpoint / path_traversal / hash_guarded_file_read / hash_reconstruction_attack / ssti_probe·identify·exploit / unicode_numeric_form_bypass / contact_report_chain / backup_source_leak / php_unserialize_magic_method /（已补）generic_param_sqli /（已补）jwt_manipulation。
5. **序列执行** `_run_strategy_sequence`：按序跑所有 `is_applicable` 的策略，**只在 `outcome.flag` 提前返回**（progress 不短路）→ 末尾追加 precondition 门控策略 = 零回归。

## 可达性矩阵

可达性缺口判据：**该类型的解题能力只在专链里（web 链不覆盖）AND 分类器可能把它误判成 web**。

| 类型 | 专链能力 | 能力质量 | 分类器触发条件 | web 链是否覆盖 | 可达性缺口 | 处置 |
|---|---|---|---|---|---|---|
| sqli | `_execute_sqli_chain`（含随便注堆叠注入解题器） | 强 | auth字段 / `select`·`union`·`sql` 出现在正文 | ✅ `generic_param_sqli` | ~~是~~ **已闭合** | `dd58a1c` |
| **jwt** | `_run_jwt_manipulation_strategy`（alg混淆/弱密钥/none） | 真·有效 | 只在**正文**见 `eyJ`/`Bearer`/`authorization` | ✅ `jwt_manipulation` | ~~是~~ **已闭合** | **本次（见下）** |
| lfi | 内联 curl（拼 `?file=`） | 弱（盲拼 base） | URL 带 `?file=`/`?path=` | ✅ file_read_endpoint + path_traversal（**比专链强**） | 否 | 无需 |
| xss | `_execute_xss_chain` | 强 | `/visit`/`document.cookie`/`onerror=`… | ✅ web 链先调 xss 链 | 否 | 无需 |
| upload | `_execute_upload_chain` | 中（多扩展名+.htaccess） | `upload`/`type=file`/`name="file"`（实测可靠） | 否 | 低（分类器稳，l33t-hoster 实测正确判 upload） | 暂缓 |
| misc | `_execute_misc_chain`（取证） | 强 | 文件扩展名（.db/.zip/.pcap…） | 部分（仅 backup_source_leak） | 低-中 | 暂缓 |
| **ssrf** | 内联 curl（盲拼 `?url=`） | **弱**（盲拼 base、不发现真参数） | 只在 URL 带 `?url=`/`?target=` | 否 | **是** | **暂缓**（见下） |
| **cmdi** | 内联 curl（盲拼 `;id`·`\|id`·`` `id` ``） | **弱**（盲拼 base） | **`detect_type` 从不返回 cmdi** | 否 | **是（最确定）** | **暂缓**（见下） |

## 本次修复：jwt 可达性（commit 见 git）

- **缺口**：`detect_type` 只查正文/URL，JWT 若在 **Cookie/Authorization header** 里就判成 web → 专 jwt 链不跑。而 `_jwt_precondition`（`strategy_registry.py:391`）查 content+html+headers+**cookies**，能力本就够，只是够不着。
- **修复**：`jwt_manipulation` 追加进 `_WEB_STRATEGY_ORDER` 末尾（与 `generic_param_sqli` 并列的 precondition 门控可达性桥）。
- **测试**：`test_web_chain_reaches_jwt_manipulation_when_token_only_in_cookie`——JWT 仅在 cookie + `detected_type="web"` 时 web 链触发 jwt 策略；无 JWT 时 precondition 拦下。零回归（全量 unit 通过）。

## 暂缓的缺口（cmdi / ssrf）及理由

cmdi、ssrf 确实是真可达性缺口（尤其 **cmdi `detect_type` 永不命中**），但**当前专链能力本身是"盲拼 base URL"的粗实现**（`{target};id`、`{target}?url=...`，不从表单/链接发现真注入点），且**不是注册的 precondition 门控策略**（是 `_execute_chain` 里的内联 curl）。直接挂进 web 链会：① 无 precondition → 每道 web 题都盲发 → 噪音/假进展；② 收益低（盲拼极少命中）。**正确做法是先把 cmdi/ssrf 重写成"参数发现 + precondition 门控"的注册策略，再按同套路接入**——属能力深度改造，单列后续任务，不在本次可达性桥接里硬塞。

## 方法论沉淀

- **两类缺口**：**可达性缺口**（已有强能力被调度够不着，如 sqli/jwt）≠ **能力深度缺口**（已有链缺某技法或实现粗糙，如 .htaccess、cmdi/ssrf 盲拼）。
- **可达性桥接套路**（已两次验证）：找到"专链里的注册策略 + 有 cookie/header 级 precondition" → 追加进 `_WEB_STRATEGY_ORDER` 末尾 → precondition 门控 + flag 才短路 ⇒ 零回归。
- **下一步**：①（深度）把 cmdi/ssrf 升级为参数发现型注册策略；② 给 jwt 找一道 live 题端到端验证；③ 同理审计 misc artifact 链在 web 分类下的可达性。
