## 0. 为什么先立这条基准

四路知识库挖掘**独立收敛到同一条**：`验证优先 = 用 runtime 外部状态证明，不信 agent 自述`。这是把「自信幻觉 flag」挡在自动提交之外的唯一闸门。

但挖掘 agent 有一处**误判**需要本基准纠正：它假设 `verifier.py` 是「扁平布尔 regex 门」。**实际并非如此** —— 现版已经按「证据来源 + runtime 强弱」分级、并对自动提交做门控。本基准的价值是：**钉死现状到底走到了哪一步**，从而精确指出还差哪几步到目标标准，避免重复造已有轮子。

## 1. 现状基线（verifier.py 实际行为）

入口 `verify_flag(state, *, flag, evidence_source, rationale, evidence_url, evidence_snippet, replayable, hypothesis_id, strategy_kind)`（`verifier.py:91`）。

### 1.1 三类证据来源（已实现的 attribution 雏形）

| 来源类 | 成员（节选） | 代码锚点 |
|---|---|---|
| **runtime（强）** | http-response, response_body, collector-hit/body/flag, command-output, rce-output, profile-photo-file-read | `:52–63` |
| **runtime（弱）** | recon, browser-rendered-page, collector-* 其余 | `:32–51` |
| **source-only** | source-leak, backup-archive, html-comment, robots-txt | `:64–73` |

### 1.2 判定与置信度（已分级，非布尔）

| 输入情形 | decision | confidence | 锚点 |
|---|---|---|---|
| flag 空 / 不匹配 `_DEFAULT_FLAG_PATTERNS` | `insufficient` | — | `:109–187`（patterns `:15–31`） |
| 此前已拒 | `rejected` | 1.0 | `:155+` |
| runtime 强来源 | `runtime`→可能 `verified` | 0.85 | `:189–393` |
| runtime 弱来源 | `runtime` | 0.45 | 同上 |
| source-only | `candidate`（需 followup） | 0.4 | `:395–436` |

### 1.3 自动提交门（已实现 reward-hacking 雏形）

`_assess_auto_submit_gate()`（`:762`）：放行 ⇔ **未限流 AND submit_confidence≥0.5 AND（seen_before OR 强来源 OR exploit 专属 rationale）**。提交经 `_attempt_submit_if_configured()`（`:494`，平台/端点）。`reject_flag()`（`:438`）显式拒收、置信 1.0、回喂策略环。

### 1.4 FlagProof 契约（现状）

`proof_type / evidence_source / evidence_url / evidence_snippet(≤200) / replayable / submit_confidence / source_trust∈{runtime,platform,source_only} / hypothesis_id / strategy_kind / timestamp`。

> **结论**：现状已具备 attribution（来源分类）+ 强弱分级 + 自动提交门 + 显式拒收 + 结构化 proof。约达目标标准的 ~70–80%。

## 2. 目标标准（committed standard）

把挖掘 §4 的 E1/E2/E6/E9 从「设想」固化为**项目验证标准**。每条标「现状差距」。

| 标准 | 内容 | 现状差距 | 出处 |
|---|---|---|---|
| **S1 双轴判定** | attribution（flag 是否逐字现于 runtime 产物）× specificity（是否匹配平台 regex/形态）。**高 specificity + 低 attribution = 幻觉**，禁自动提交 | 现按来源分级，但**未显式把「regex 完美但 grounding 仅模型断言」单列为 REVIEW** | E1, BB-228 |
| **S2 三态裁决** | `ACCEPT`（强 runtime→自动交）/`REVIEW`（便宜 reviewer→人）/`REJECT`（reason 回喂） | 现 5 态（insufficient/rejected/runtime/verified/candidate）语义接近，但**缺统一 verdict enum + reason 路由**；`runtime/candidate` 应显式归入 REVIEW | E2 |
| **S3 runtime-grounding 必填** | 仅静态/源码/自写 notes 来源的 flag **禁** AUTO_SUBMIT；runtime-grounding 是自动提交的硬前提 | 门控已含「强来源」，但 source-only→candidate 仍可能经 seen_before 放行，需收紧为硬前提 | E9/C10, BB-367/459 |
| **S4 SARIF 式 FlagProof** | proof 从扁平串升为节点图：产物 + 来源分类 + 因果步链(codeFlow) + 产生它的 tool call；「源码见到」结构性区别于「runtime 触发」 | 现 FlagProof 为扁平字段，**无 codeFlow/relatedLocation 因果链** | E6, BB-318 |
| **S5 确定性回归门** | 已解题录 replay fixture（用 S4 proof）；合并前跑 L1 确定性 grounding（无 API）→L2 批量 judge→L3 全轨迹，**AND 门，一题回归即拦** | **无 replay 回归套件** | E8, BB-228/240 |

## 3. 解题判定的硬规则（done-criteria）

「task 解出」当且仅当全部成立（落 verifier + finish）：

1. flag 匹配平台形态（specificity）✔ 现已实现 `:15–31`。
2. flag 逐字出现在 **runtime 产物**（attribution，非源码注释/自写 notes/模型断言）。
3. 干净会话可复现（replayable=true，S4 proof 可回放）。
4. 黑板无矛盾证据（无同名 flag 被 reject 记录）。

不满足 2/3 → 最高 `REVIEW`，**不得 AUTO_SUBMIT**。
