# 数据治理与知识回填 policy（产出数据怎么放 / 什么回填知识库）

**日期**：2026-06-29 · **状态**：拍板生效（用户 2026-06-29 选 A「先立规矩」）

回答一个长期含糊的问题：FlagHunter 跑起来会产出一堆文件 —— **哪些是可丢弃的原始
产出、哪些回填进知识库、哪些回写项目治理文档**。本文是这件事的单一真相源。

一句话心智模型：

> **`loot/` 是临时产物区，`knowledge/sources/` 是精选知识库，`knowledge/{ctf_,}sessions/`
> 是自动草稿箱，`docs/dev/*_WP_*.md` 是人工审核的题解，仓库内权威文档是项目治理真相源。**

---

## 四层数据（亲核自实际落点 + .gitignore + git ls-files）

| 层 | 产出文件（举例） | 落点 | git | 性质 / 谁消费 |
|---|---|---|---|---|
| **① 原始 run 产物** | `notes.json`、`provenance.jsonl`(P3 工具溯源)、`artifact_registry/*.jsonl`(每题溯源)、`session_ledgers/`、`checkpoints/`、`metrics/`、`reports/`、`*.log`、OCR 截图 PNG | `loot/` | ❌ `loot/*` 全 ignore | **单次 run 原始产物,可丢弃**。不进仓 |
| **① 机器学习态** | `strategy_memory.json`(P1 负反馈/策略库)、`target_profiles/` | `loot/` | ❌ ignore | 机器读写,运行时 `project_memory.py` 喂回 prompt。**机器记忆 ≠ 人读知识库** |
| **② RAG 知识库(精选)** | `web_sqli.md` `web_ssrf.md` `recon_methodology.md` 等 | `flaghunter/knowledge/sources/` | ✅ **跟踪** | **人工精选**,跨 run RAG 检索的真知识库 |
| **② 自动回填草稿** | `ctf_experience`→`knowledge/ctf_sessions/*.md`；`session_writer`→`knowledge/sessions/*.md`(仅 high/medium 的 finding/vuln/cred)；`retrospective.json` | `flaghunter/knowledge/` | ❌ **全 ignore**（本策略统一） | run 自动产出→`indexer` 扫→本机 RAG 复用。**本地缓存,不进仓** |
| **③ 人工审核题解 WP** | `docs/dev/DASCTF_*_WP_*.md` | `docs/dev/` | ✅ 跟踪 | 经人工审核的题解与阶段记录,随仓流通 |
| **④ 项目决策与治理记录** | `AGENTS.md`、`docs/optimization-guide.md`、相关 ADR | 仓库内既有权威文档 | ✅ 跟踪 | **跨会话项目认知**:稳定约束、架构决策、教训和能力缺口模式。非解题数据 |

## 路由规则（产出后该往哪走）

1. **原始 run 数据**（日志/截图/全量 provenance/strategy_memory）→ 留 `loot/`，**永不进仓、可定期清理**。调试完即可删；机器学习态（strategy_memory / target_profiles）保留以喂下次 run，但仅限本机。

2. **可复用解题知识**（"某题型什么链路打通了"）：
   - 框架**自动**写入 `knowledge/ctf_sessions/` & `sessions/`（本地 RAG 草稿箱，**不进仓**）。
   - 其中**值得长期复用**的，经人工审核和蒸馏后写进 `knowledge/sources/*.md`（**committed**，进 RAG + 随仓流通）。**进仓只走这一条人工审核通道。**

3. **一道题的完整打法** → 写 `docs/dev/<赛事>_<题>_WP_<日期>_V1.md`（committed，对标已有 DASCTF WP）。

4. **框架级教训**（一个缺口、一次"能力写好了却够不着"、一个决策、一条反馈）→ 回写最相关的既有权威文档：稳定约束进 `AGENTS.md`，综合风险与路线进 `docs/optimization-guide.md`，架构取舍进对应 ADR。**不创建工具专属项目记忆，也不在治理文档中堆放解题细节。**

### 判别口诀
- 「这是这次 run 的临时垃圾吗?」→ `loot/`。
- 「下次遇到同类型题，这条知识能直接复用吗?」→ 蒸馏进 `knowledge/sources/`。
- 「这是这道题怎么打的完整记录吗?」→ `docs/dev/*_WP_*.md`。
- 「这是关于*框架本身*怎么改/为什么这么决策的吗?」→ 最相关的仓库内权威文档。

## 本次修正的不一致

`.gitignore` 原来只 ignore 了 `knowledge/sessions/`，**漏了 `knowledge/ctf_sessions/`** ——
意味着自动写的解题草稿会在 `git add knowledge/` 时悄悄进仓，与"自动产出只留本地、
进仓只走人工蒸馏"的规则冲突。

**修正**：`.gitignore` 追加 `/flaghunter/knowledge/ctf_sessions/`，与 `sessions/`、
`retrospective*` 对齐。自此**所有自动回填草稿一律本地，进仓只有 `sources/` 与
`docs/dev` 题解。**

## 跑靶场（dasctf 等）时这套闭环怎么转

`ctf2.dasctf.com/dashboard/practice` 等靶场，**仅对授权/自有账号的题目实例跑**。
一次真跑会自然分流：

- 原始数据 → `loot/`（可丢）
- 解题经验 → `knowledge/ctf_sessions/`（自动、本地 RAG）
- 打通的题 → 我写 `docs/dev/*_WP_*.md` + 蒸馏可复用部分进 `knowledge/sources/`
- 框架级教训 → 蒸馏后回填最相关的仓库内权威文档

即本文是「真跑后产出怎么归位」的执行手册。
