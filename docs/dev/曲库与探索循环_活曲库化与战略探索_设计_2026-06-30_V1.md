## 0. 缘起与定位

压测 bestphp's revenge（强网杯2019，SoapClient SSRF + session 反序列化）暴露 FlagHunter
CTF web 解题的结构天花板（详见本文件后续分析、`FlagHunter_目标架构_北极星_2026-06-27_V3.md` 与本仓 Git 历史）：

> CTF web 解题是"预置攻击链曲库驱动"，不是开放式自主探索。dispatcher 只检封闭集的
> exploit 模式；曲库外的漏洞类（如 SoapClient SSRF+反序列化）**结构上发现不了** →
> 跑完固定 pipeline 就"收敛"放弃，真 agent 循环不启动。

本设计的参考来源：`D:\newwork\AI-Agents\aiagentstudy\`（一个精选 AI-agent 知识库，
其**自身工程架构**就是"活曲库"的范本）。所有设计点都标注了该库内的证据路径。

### 0.1 两条正交轴（重要：别混）

两轴有交集（三角色解耦会同时服务两者），但**轴 B 是更大重构，现在不动**。本文档只做轴 A。

## 1. 核心认知：把"门控逻辑"和"模式知识"拆开

现状：`_has_jwt_surface` / `_has_tornado_feature` 等约 25 个 `_has_*` 结构探测器（门控）
与各 chain 的 exploit 链（知识）**焊死**成硬编码封闭集（见 `hypothesis_engine.py`
`_rule_based_hypotheses` + `_CHAIN_BY_KIND`）。死的、不可检索、不能生长。

根本改造方向（参考库的根本洞察）：**门控仍是确定性代码，知识变成可检索、可生长的数据。**

### 1.1 关键事实：参考库的检索全程零随机（对我们是好消息）

参考库的检索**不是** dense+BM25，而是**纯确定性**管线：
- item 级 FTS5（trigram 分词，中文友好）+ chunk 级 FTS5（1400 字符/220 重叠切块），
  各自 BM25 排名 → RRF 融合（`RRF_K=60`）→ 纯规则 rerank（标题/标签/takeaway/意图加权）
  → `(-score, id)` 排序。证据：`knowledge/raw/build-kb-fts.py`、`knowledge/raw/query-kb.py:467-616,274-354`。
- 向量/语义检索是蓝图里**明确未做的 P3**：`knowledge/catalog/knowledge-system-optimization.md`。

> **结论**：整条管线零随机、可复现，正好满足 FlagHunter「曲库命中要字节级一致、不引入
> 随机性」的硬约束。我们照抄这套确定性检索，**不碰嵌入模型**。

## 2. 曲库怎么搭（活曲库 = schema 化 + 确定性检索 + 生长闭环）

| # | 改造点 | 做法 | 参考证据（aiagentstudy 内） |
|---|---|---|---|
| ① | 每个 kind 外化成"攻击模式 item" | `attack_patterns/<kind>/pattern.json + recipe.md + raw/`。双轨：recipe.md 人读真相源，pattern.json 是 dispatcher 读的契约（`id/kind/title/status/topic(=漏洞族)/aliases[]/signals[]/exploit_chain_ref/evidence_paths[]`）。**exploit 链仍是硬编码代码**，pattern.json 只是其可检索元数据 → 命中跑的还是同一段字节级链 | `item.json` vs `summary.md` 双轨；`knowledge/schema/README.md`；样例 `knowledge/items/01-context-memory/BB-2026-05-01-001/` |
| ② | 确定性检索做"曲库初筛"，`_has_*` 做最终门控 | 题目指纹（响应头/报错串/框架指纹/cookie 名）当 query → BM25×RRF 召回 top-k 候选 kind → 只对这 k 个跑各自 `_has_*` 确认。**召回(检索)+精确(探测器)两层都确定性**，命中题字节级一致；曲库长到几百条不退化（破解线性扫 25 个） | `query-kb.py`、`build-kb-fts.py` |
| ③ | aliases 同义词表提指纹召回 | 每 kind 配一组别名/指纹同义词（`Tornado↔tornado.web↔{{}}`；`SoapClient↔SSRF↔反序列化`），**建索引时注入**，新指纹只改表不碰探测器代码 | `knowledge/retrieval/aliases.json`、`build-kb-fts.py:223,258` |
| ④ | **miss → candidate radar 四文件状态机** | `repertoire_miss` 的题落 `inbox.jsonl` 候选（题目指纹+触发探测器+证据路径指向 ctf_sessions+`reason`）；状态机 `inbox→promoted/deferred/rejected`，promote 带门禁（去重/dry-run/质量门/`status_history`）；**进仓走人工蒸馏**（禁批量 promote） | `knowledge/candidates/README.md`；`knowledge/raw/manage_candidates.py:1095-1334` |
| ⑤ | golden eval 守字节级回归 | `eval/pattern-queries.jsonl: {fingerprint_query → expected_kind}`，跑 hit@k / MRR / nDCG。每加模式/改 alias 跑一遍，确认老题命中 kind 与顺序没变 | `knowledge/raw/eval-search.py`、`knowledge/retrieval/evals/search-queries.jsonl` |
| ⑥ | （可选）低 token catalog 给 planner | `attack_patterns/catalog.md`（kind → 一句话触发条件 + 链摘要），planner 先读目录决定方向再下钻（progressive disclosure） | `knowledge/catalog/map.md` |

### 2.1 ④ 与现有数据治理同构（直接复用，不另起炉灶）

`数据治理与知识回填_policy_2026-06-29_V1.md` 的四层路由与参考库的 radar 完全同构：

## 3. 探索循环怎么走（战术单步 → 战略开放探索）

骨架不是单层 ReAct，而是**三角色解耦 + 带 value 的假设树 + 验证回路(检测/修正分离)
+ goal+budget 停止准则 + 外部化状态**。逐条给 FlagHunter 落点与证据：

1. **假设树替线性队列（最大结构短板的直接解药）。** LATS（MCTS+value+self-reflection+
   环境反馈）把 `HypothesisEngine` 从线性 checklist 升级成搜索树：每节点=候选漏洞假设，
   带 value/扩展预算/回溯；`stop_no_progress` 改为"**主分支价值下降才切替代分支**"而非到点
   停机；失败信号回传父节点剪枝（落 `RecoveryController`）。
   证据：`knowledge/items/03-control-loop/BB-2026-05-01-308/summary.md`（该篇**直接点名**
   我们的 HypothesisEngine / stop_no_progress / RecoveryController）。

2. **`repertoire_miss` = escalation 触发器（已交付，见 §5）。** completeness-critic 模式：
   所有曲库内分支 value 耗尽时**不收敛放弃**，而是触发"升级到自由探索 sub-agent"。
   证据：`BB-2026-05-01-188/summary.md`（无障碍 agent：显式登记盲区 + escalation checkpoint）。

3. **Detect→Identify→Exploit 分阶段策略（"曲库外怎么探索"的真正机制）。** 把 web 攻击链从
   固定 pipeline 改写成分阶段：先通用探测（算术 payload / token 普查）→ 再指纹识别（引擎/
   框架/格式推断）→ 才发 exploit，每阶段产**分层证据**驱动下一步。这是让 agent 在曲库外
   **设计跨多步实验**（如 SoapClient SSRF）的领域骨架。反对盲打字典。
   证据：`knowledge/items/05-security-techniques/BB-2026-05-01-312/313/315/summary.md`
   （SSTI Detect/Identify/Exploit；SignSaboteur token 普查→框架识别→密钥猜测→篡改→授权复验）。

4. **goal+budget+证据停止准则**替 8 步硬预算：显式声明 goal 与 token/动作预算，达成或
   耗尽才停，**停时必须产 FlagProof 证据**，区分 source-only / runtime-triggered。
   证据：`BB-2026-05-01-010`（Codex `/goal`）、`419`（查 DB 真状态防 faking）、`423`（自信但错）。

5. **验证回路：检测与修正分离。** wrong-flag/无效 payload 后，先用**确定性 validator**
   检测+解释失败，再把**精确失败信息**回喂做定向修正，失败沉淀成可检索负反馈（落已有
   `strategy_memory`）。LLM 擅长修特定错、不擅长发现自己的错。
   证据：`BB-2026-05-01-310`（CRITIC：生成/验证分两步）、`574`（检测/修正分离）、
   `309`（Reflexion 短小可检索的 verbal reflection）、`361`（SkillOpt 负反馈缓冲）。

### 3.1 成本侧

现有成本分层路由（以当前 provider 配置代码和 `AGENTS.md` 为准）可加"角色维度"：Explorer/Planner 走
便宜快模型大量发散、Judge/exploit-worker 走强模型坐实；并套 circuit breaker（tool-spend
硬上限）。证据：`BB-2026-05-01-024`、`191`。

## 6. 诚实边界

- 三角色解耦（Planner/Worker/Judge）是更大重构，绑在轴 B（330/331），**现在不动**。本轴先把
  "假设树 + 分阶段探索 + miss 生长闭环"做扎实。
- 即便脚手架齐了，也**不保证** gpt-5.4 真能解出 bestphp。本设计的价值是把"能不能尝试"
  和"尝试成不成功"解耦——让循环**结构上能去试**曲库外的题。
- 参考库 `query-kb.py` 的 FTS 当前因 sqlite `trigram` tokenizer 缺失会报错；若后续要在
  FlagHunter 复用其检索代码，需确认 sqlite 编译带 FTS5 trigram，或改用其它确定性分词。
