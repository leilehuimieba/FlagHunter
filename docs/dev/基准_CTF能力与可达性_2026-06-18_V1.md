## 0. 这份基准要钉死什么

「**能力写好却够不着**」是本项目反复记录的失败模式（[随便注 SQLi] 解题器写好却被分类误判够不着，6m27s 未解）。它不是偶发 bug，是**注册面（能写多少策略）与分发面（调度真能走到几个）天然会漂移**的结构问题。

本基准做三件事，且必须随代码维护：

1. **冻结注册清单**：当前注册了哪些策略、各属哪条链、precondition 看什么（§2）。
2. **钉死分发闭包**：一条链在什么条件下才会被进入，从而推出每个策略「是否够得着」（§3 + §4 矩阵）。
3. **立不变量 + 守护测试**：把「每个注册策略至少一条路径可达」变成 CI 拦得住的 **I5**（§5）。

> 写法原则：**只写代码里能 grep 到的事实**，每条带 `file:line`。静态分析不确定处显式标 ⚠️，不拍脑袋下「可达/不可达」结论。

## 1. 两条分发路径（理解可达性的前提）

策略能不能跑，取决于**它所属的链会不会被进入**。链顺序由 `HypothesisEngine.choose_chain_order()` 决定（`hypothesis_engine.py:113`）：

```
chain_order = [detected_type(非 web/auto)] + [ranked 假设经 _CHAIN_BY_KIND 映射的链] + ["web" 永远兜底]
```

进入某链后，由 registry 驱动分发（关节 B，P3）跑该链下 precondition 命中的策略。因此**一个策略可达 ⇔ 它能被以下任一路径触达**：

| 路径 | 机制 | 代码锚点 |
|---|---|---|
| **P-detect** | `detect_type(page_source,url)` 返回该策略所属 `chain_name` | `ctf_planner.py:320`，返回值集合见 §3.1 |
| **P-hypo** | `_rule_based_hypotheses` 生成某 kind 的假设，`_CHAIN_BY_KIND[kind]` = 该链 | `hypothesis_engine.py:11`（映射表）、`:328+`（生成规则） |
| **P-webbridge** | 该策略名被显式列进 web 链的 `web_strategy_order`（precondition 门控、flag 才短路 ⇒ 零回归） | `chains/web.py:44` |

**关键认知**：`_CHAIN_BY_KIND`（kind→链的映射表，41 项）里**有**某 kind，不等于该 kind 的假设**会被生成**。映射表只是「如果生成了往哪条链放」；真正决定可达性的是 detect_type 输出 ∪ 实际生成的假设 kind ∪ web 桥接清单。**ground-truth 分析最容易在这里误报**（只看映射表 → 误判可达；只看假设生成 → 漏掉 detect_type / web 桥接）。

### 3.2 实际被生成的假设 kind（P-hypo 能进哪些链）

- 关键字风格：`generic_web_recon`(`:601`)、`llm_driven_exploration`(`:626`) → 均映射 `web`。

### 4.1 确认缺口（P0 正确性）

- **`graphql_introspection`、`nosql_injection`**：已注册（`:886`/`:901`）、有 execute 包装（`:467`/`:499`），但三条路径**全不命中** —— detect_type 不产出 graphql/nosql、无规则生成对应假设、不在 web 桥接。**任何 `chain_order` 都不会进 `graphql`/`nosql` 链**，能力 100% 够不着。
  - **背景**：二者是 P4「New strategies」新增（`hypothesis_engine.py:37–40` 注释）。本基准证明 P4 **重新引入了一次「能力存在却够不着」**，与历史 [随便注] 同构。
  - **推荐修法**（沿用已多次验证的「可达性桥接套路」，零回归）：把 `"graphql_introspection"`、`"nosql_injection"` 追加进 `chains/web.py:44` 的 `web_strategy_order` 末尾（precondition 已分别在 `_graphql_precondition`/`_nosql_precondition` 门控），各补一条 web 链端到端单测。**此修改落在 P4 范围内，由负责 P4 的同学执行**；本基准只负责钉死缺口与修法。

### 4.2 疑似退役（待确认，勿误删）

- **`ssti_via_render_parameter`、`tornado_ssti`**（`chain_name="web-legacy"`）：`web-legacy` 链不在任何 chain_order 来源里，三阶段 `ssti_probe/identify/exploit` 已在 web 桥接覆盖同一面。**判断**：很可能是有意保留的旧实现而非 bug。**处置建议**：要么显式标注 `@deprecated` 并移出 `build_default`，要么从 registry 删除——否则 §5 的不变量测试会把它们报成可达性缺口。**需人确认意图后再动**。

## 5. 不变量 I5 + 守护测试（防回归的机制）

> **I5（可达性不变量）**：`StrategyRegistry.build_default()` 注册的每个策略，必须存在至少一条 §1 的分发路径能触达它（除非显式标记 `deprecated`）。

这是把本基准从「一次性快照」变成「CI 拦得住」的关键。守护测试规格（**待实现**，建议落 `tests/unit/agents/test_strategy_reachability.py`）：

1. 取 `build_default()` 全部策略 → 其 `chain_name` 集合。
2. 计算**可达链闭包** = `detect_type` 返回值集合（§3.1，硬编码 + 注释指向 ctf_planner）∪ `_rule_based_hypotheses` 实际生成 kind 经 `_CHAIN_BY_KIND` 映射的链 ∪ `chains/web.py:web_strategy_order` 命名的策略所属面。
3. 断言：每个非 deprecated 策略的可达性成立；任何不可达策略 → **测试 FAIL，列出策略名 + 缺哪条路径**。
4. （增强）对每个策略给一组 `(target,hint,page_features)` fixture，断言其 precondition 在该 fixture 下为真且能在对应 chain 序列里被 `is_applicable` 选中。

落地后，新增策略若忘记接分发，CI 立即红，而不是等某道 live 题 6 分钟未解才暴露。

## 6. 维护规则

改动以下任一处，**必须回到本文更新 §2/§3/§4 并跑 I5 测试**：

- 新增/删除注册策略（`strategy_registry.py:_register_*`）
- 改 `detect_type` 返回集合（`ctf_planner.py`）
- 改 `_CHAIN_BY_KIND` 或假设生成规则（`hypothesis_engine.py`）
- 改 `chains/web.py:web_strategy_order` 桥接清单
