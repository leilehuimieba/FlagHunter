## 0. 心法：文档是「控制面」，不是交作业

> **每一份文档都对应一个"决策"和一道"闸门"：它回答一个问题，并锁住一个之后不许随便改的东西。不产生决策、不锁边界的文档 = 负债。**

推论：

- 文档按"锁住什么"分层，不按"写得多全"评价。
- 现状类文档（基准）必须配**守护测试**，否则三天过期。
- 唯一真相源（single source of truth）优先于任何口头约定：冲突以 `docs/README.md` + ADR + 基准为准。

## 1. 七阶段生命周期

```
愿景 → 架构方向 → 决策记录 → 实施计划 → 基准线 → 逐功能开发 → 测试 → 发布
```

每阶段：**产出什么文档 → 锁住什么 → FlagHunter 落点**。

| 阶段 | 产出文档 | 锁住什么 | FlagHunter 落点 |
|---|---|---|---|
| 0 愿景/边界 | README、CLAUDE.md、AGENTS.md、**合规授权边界** | 做什么/不做什么/**法律红线** | ✅ 已有（"仅授权红队/CTF/教育"） |
| 1 架构方向 | 架构方向文档 | **怎么"想"**：领域模型、对标、核心抽象 | ✅ `FlagHunter_红队智能体架构…V2` |
| 2 架构决策(ADR) | ADR + **不变量** | 选了哪条路+为什么+放弃什么+不变量 | ✅ ADR（I1–I4） |
| 3 实施计划 | 阶段化路线 + 里程碑 + 验收 + 风险登记 | **什么顺序、里程碑、完成定义(DoD)** | ✅ P0–P5 + TaskList（可补独立计划书） |
| 4 基准线 | 现状(带 file:line) + 不变量 + 守护测试 | **拿什么尺子量、哪些不许退化** | ✅ 三份 `基准_*` + I5 |
| 5 逐功能开发 | 功能规格 + 提交历史 | 每个功能的 DoD、垂直切片 | ✅ chains 逐切片、小步 commit |
| 6 测试 | 分层测试 + 回归门 | **防回归** | ⚠️ unit/integration 有，eval/守护待补 |
| 7 发布/运维 | release 流程 + CHANGELOG + 版本 | **怎么对外、schema 怎么迁移** | ✅ release-* + CHANGELOG_schema |

**关键纪律**：

- ADR 只增不改——要改决策，写新 ADR 标"取代旧的"。
- 不变量是 ADR 的灵魂（"依赖单向向下""事件单源""每注册策略可达"），靠测试守、不靠自觉。
- 实施计划要**自顶向下、垂直切片**：先把骨架与层间契约定死，再逐层下沉；别横着把所有层都铺一半（graphql/nosql 可达性缺口正是"先把策略写完才接分发"的横向开发后果）。

## 2. 逐功能内循环（阶段 5 展开）

"开发功能"不是盲目点 yes，而是每个功能走同一内循环：

```
①写规格(输入/输出/成功信号/边界)
   ↓
②先写测试(test-first：红)——把"完成"变成可执行断言
   ↓
③最小实现(让测试变绿)
   ↓
④验证(跑该模块测试 + 相关守护测试，确认没破不变量)
   ↓
⑤一个逻辑单元一个 commit
   ↓
回到① 下一个垂直切片
```

**完成定义（Definition of Done）**——满足全部才算 done：

1. 规格写了（哪怕一段话）。
2. 测试绿了（含相关守护测试）。
3. 不变量没破。
4. 受影响的文档/基准同步了。

**垂直切片**：每次交付一条能端到端走通的最窄链路（如"随便注"：分类→分发→策略→验证 全打通），而不是攒一堆够不着的能力。

## 3. 测试分层（阶段 6 展开）

AI agent 项目比普通项目多两层（守护 + eval）：

| 层 | 测什么 | 现状 |
|---|---|---|
| 单元 unit | 单函数/类逻辑（确定性） | ✅ `tests/unit/` |
| 集成 integration | 模块拼接 | ✅ `tests/integration/` |
| **守护/不变量** | 架构约束不被破坏（I5 可达性、依赖单向） | ⚠️ I5 守护测试已落（`tests/unit/agents/test_strategy_reachability.py`），其余不变量待补 |
| 端到端 e2e | 真靶机完整解题链 | ✅ live 台账（部分） |
| **Eval/回放（agent 特有）** | 已解题录 replay fixture，改动后确定性重跑；judge 只判边界 | ⚠️ **最小骨架已落**（`flaghunter/eval/` + `tests/eval/`，2 金标准 fixture 确定性复现）；自动录制/分层 judge 待补 |
| 回归门（CI） | 合并前自动跑上面几层，一题回归即拦 | ⚠️ 待建 |

> 心法：**AI agent 的"测试"核心不是 unit，是 eval harness**——模型不确定，必须用"金标准轨迹 + 回放"证明"改了 prompt/策略没把已解的题搞挂"。这是与普通 CRUD 项目最大的不同。

## 4. 宏观调控（单人 + AI 怎么不失控）

四条机制，核心是**唯一真相源 + 自动守护**：

1. **唯一真相源**：`docs/README.md`（总入口）、ADR（架构真相）、基准（现状真相）。任何冲突以它们为准。
2. **不变量靠测试守**：I1–I5 每条配守护测试，破了 CI 红。单人项目最省心的护城河——三个月后忘了的约束，测试替你记着。
3. **WIP 限制**：同时只推一个 P 阶段（当前 P4 in_progress），别并行铺四条。
4. **solo 周循环**：
   - 周初：看板对齐（P 阶段进度 + 基准有没有变红）→ 选本周一条垂直切片。
   - 期间：内循环（规格→测试→实现→提交），小步 commit。
   - 周末：跑全量测试 + 更新受影响 ADR/基准 + 沉淀一条经验/记忆。

## 6. 维护规则

- 流程/阶段/机制有实质变化 → 更新本文。
- 不变量新增/修改 → 同步 ADR + 对应守护测试。
- 本文是"流程的控制面"，与 ADR（架构控制面）、基准（现状控制面）三足并立，均挂在 `docs/README.md`。
