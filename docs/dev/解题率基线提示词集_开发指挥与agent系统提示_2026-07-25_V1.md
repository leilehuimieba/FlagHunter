## 这份文档是什么

用户要两类提示词:

1. **Set A — 开发指挥提示词**:站在开发工程师视角,copy-paste 给 Claude Code 让它替你
   推进基线主线(建题库 / 跑一轮出报告 / 诊断单题 / 修可达性缺口 / 拆巨石)。这些是给
   **我(Claude Code)** 的输入。
2. **Set B — agent 内部系统提示**:站在渗透工程师视角,治 FlagHunter 求解 agent 的三种
   病——**fixation(固着,反复砸同一招)/ spinning(空转,进度停滞却不停手)/ directness
   (绕远,题面点名的向量偏偏最后才试)**。这些是给 **FlagHunter 求解循环里的大模型** 的
   输入。

一条设计铁律贯穿全篇([[feedback_less_is_more_dont_cage_llm]]):**代码只给约束边界,
不把大模型关进笼子。** 三种病的**主要**治理在代码侧——黑板 loop 的确定性 substrate
(`_run_solve_loop` / `choose_chain_order` no-LLM 基座)结构性地枚举链、去重探测面、
标记 dead-end;可达性缺口靠"桥接末尾追加"补(`bab6e7f` 登录框 SQLi、`9b9aef3` 路径段
SSTI)。系统提示是**当 LLM brain 在驱动时的互补 nudge**,不是替代。Set B 因此先盘点
代码里已有的,再只补真空档,且停在原则层,不写死步数/规则树。

## Set A — 开发指挥提示词

每条:**何时用 → 提示词正文(copy 区)→ 期望产出**。这些是可直接粘贴的祈使句。

### A1 · 建 / 扩基线题库

何时用:要往 corpus 加题,或调整分层。

```
在 flaghunter/eval/baseline/corpus.json 里加 N 道 <Tier> 题。用 opencli(yeeqaype
profile)从 ctf2.dasctf.com/practice 选题,只存稳定元数据(id/name/category/tier/
known_flag/task),不存 live URL。分层规则:T0=冒烟锚(可留手法提示,只做回归);
T1=编目内单链(中性 task,只给"拿flag"目标,不喂手法);T2=多步链;T3=编目外天花板。
加完跑 python -m flaghunter.eval.baseline --dry-run 确认离线冒烟绿,再按逻辑 commit。
```

期望产出:corpus.json 追加条目 + 去重守卫仍绿 + 一个 commit。

### A2 · 跑一轮基线并出记分卡

何时用:靶机已部署、拿到临时 URL,要跑一轮真实解题率。

```
用 --targets id=url 注入这些实例,跑基线 sweep(subprocess 逐题隔离,三轴护栏
timeout×max_loops×隔离 STRATEGY_MEMORY_PATH)。判定只读 stdout+report 外部面,不碰
dispatcher 内部。跑完把分层记分卡合并到 loot/baseline/<date>_runN/,给我:solve@1、
每题 verdict/steps/耗时/cold|warm、以及任何 spinning/fixation/directness 的信号。无
target 的题记 SKIPPED,不要静默当通过。
```

期望产出:scorecard.json + report.md + 一段人读小结(哪些稳、哪题是诊断失败)。

### A3 · 诊断单题失败(冷/暖偏离)

何时用:某题 FAIL 或冷暖表现反常,要根因。

```
<题名> 这一轮 <FAIL/spinning/冷暖反转>。别急着改代码:先复盘这题的 trace(黑板
observations / tools_used / 每步 rationale),定位是哪一层够不着——是探测面收集不到真
注入点(可达性缺口)、还是负反馈粒度太粗把制胜向量一起放弃了、还是跨工具旋转没被标
dead-end。给我一句话根因 + 最小修法方向 + 同构先例(bab6e7f/9b9aef3/5cd0d6d 里哪个)。
先亲核再动手。
```

期望产出:一句话根因 + 最小 diff 方向 + 先例锚点(**不**直接改码,先对齐)。

### A4 · 修可达性缺口(能力已写好但够不着)

何时用:A3 定位到"链/executor 已存在,但探测面/前置门够不着真注入点"。

```
这是可达性缺口,同构 bab6e7f(登录框 SQLi)/9b9aef3(路径段 SSTI):能力在,探测面够
不着。按那个模式修——在 WEB_STRATEGY_ORDER / 探测面收集 / 注入函数里补桥接,precondition
+ verification 双 gate,候选只从稳定 page_features 派生(别用累积 observation,否则
surface-exhaustion 签名跨 pass 漂移)。写一个确定性 acceptance 测(全非目标面返错、用
非 seed 的路由证 discovered-link 派生),再对 tests/integration+tests/unit/agents 跑门,
零回归后按逻辑 commit。别 push,我来决定。
```

期望产出:三层桥接修复 + 确定性 acceptance 守护测 + 零回归 + 一个 commit。

## Set B — agent 内部系统提示

### 先盘点:代码里已经有什么

**不要重造。** 三病的结构性治理已在:

- `blackboard_brain._SYSTEM_PROMPT`(blackboard_brain.py:40)已明写:
  - **directness**:"most direct progress toward the flag — prefer the shortest remaining
    path (high value, high directness)"
  - **fixation**:"Read ATTEMPTS as negative feedback: a tool already run several times
    with NO progress is a dead end — switch to a DIFFERENT tool or tactic"
  - **never re-try a REFUTED intent**
- `_fmt_attempt`(:85)把每工具尝试渲染成 `NO progress -> dead end` / `spinning, switch`
  / `N made progress`——**spinning 的逐工具信号**。
- `_cross_tool_spinning_note`(:104)聚合**跨工具旋转**线索(web→lfi→misc→web 每步各自
  满足"switch"却整体不前进→升级或换根本不同向量)。**Advisory only**,是 hint 不是规则。
- 确定性 substrate:`_known_failed_payloads` 播种链、净负反馈粒度精确到"这条向量"
  (`5cd0d6d`)、可达性桥接(`bab6e7f`/`9b9aef3`)。
- `pa_agent.jinja`:plan 执行纪律 + Anti-Hallucination(每个 claim 必须有 tool 结果背书)。

所以 Set B 的价值是:**把上述散在代码里的原则,收敛成一段可读、可贴、可对齐的系统提示
增量**,并标清哪条已 wire、哪条是增量、落点在哪。

### B1 · 每步三段式纪律

每个动作前,脑内(或 rationale 里)成形三段:

```
每一步选动作前,先想清三件事,并把前两件压进 rationale/expected_signal:
1. 最高价值假设 + 依据:此刻最短路径上最可能通向 flag 的是哪条?依据是题面/已确认
   FACT 的哪一点?
2. 预期证据:如果这步成功,tool 输出里会出现什么字符串?(填进 expected_signal)
3. 失败 fallback:如果没出现该证据,下一步换什么——而不是把同一招再砸一遍。
```

落点:`_SYSTEM_PROMPT` 已要求 `expected_signal` 和 `rationale`;本条是把"依据 + fallback"
明确化的**增量措辞**,可并入 `_SYSTEM_PROMPT` 的 reply-shape 说明段。

### B2 · fixation —— 无新证据禁重复同类,负反馈是"这条向量"

```
没有新证据(新的 FACT / 新的响应特征)出现时,不要重复同一类 payload。ATTEMPTS 里
标 "NO progress -> dead end" 的工具,换掉。但注意:负反馈针对的是"这条具体向量",
不是"整类技术"——"泛参 GET sqli 打空了"不等于"放弃所有 SQLi",登录框 POST 注入仍
可能是制胜路径。别把一次向量失败读成整类放弃。
```

落点:`_SYSTEM_PROMPT` dead-end 段的**增量**——补"粒度=向量非整类"这半句(代码侧
`5cd0d6d` 已做净负反馈粒度,这是把同一粒度讲给 brain 听)。

### B3 · spinning —— 连 N 次无实质进展就换根本不同的向量

```
"进度"指出现了新的、不同的结果,不是把同一个看起来有用的输出反复重放。同一工具跑了
多次却只有一两种 distinct 结果(spinning),等价于 dead end:换工具。若两个以上工具
同时 stalled(CROSS-TOOL SPINNING 提示出现),说明整条旋转链已耗尽——升级(问"要不要
编目外的链")或换一个根本不同的攻击面,不要转回去接着轮。
```

落点:**已 wire**(`_fmt_attempt` 的 `spinning, switch` + `_cross_tool_spinning_note`)。
本条是把已有渲染背后的**意图**讲清,便于后续复盘对齐;不需要再改代码。

### B4 · directness —— 题面点名的向量先试,登录框优先 form 注入

```
题面/源码/响应里点到的向量,先试。看到登录表单,优先对 form 字段做注入(POST),
别先去泛化 GET 参数扫。看到模板框架指纹(jinja/flask/render_template_string),优先
SSTI 探测,注入点可能在 URL 路径段而非 query。最短路径优先于"把所有面都扫一遍"。
```

落点:`_SYSTEM_PROMPT` directness 段的**增量**。代码侧可达性已由 `bab6e7f`(登录框
SQLi 桥接)/`9b9aef3`(路径段 SSTI 桥接)结构性保证够得着;本条让 brain 在有 LLM 驱动
时也**先**选它,减少靠 ATTEMPTS 自纠的延迟(首轮 shrine/EasySQL 的 directness 病根)。

### B5 · repertoire_miss —— 够不着就升级为显式判断,别散射

```
如果编目内的链都试过、都够不着真注入点(repertoire miss),不要退化成在各工具间散射。
把它升级成一个显式判断:"这题需要一条编目外的链吗?"——明确说出缺的是什么向量,而不是
继续无目标地轮换已知工具。
```

落点:**增量**,可并入 `_SYSTEM_PROMPT` 结尾。代码侧 `is_repertoire_miss` 已是单一真相源
([[project_ctf_autonomy_ceiling]]),这是把该信号的**应对**讲给 brain。
